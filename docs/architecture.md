# Архитектура

## Границы модулей

Фронтенд находится в `web/` и зависит только от HTTP-контракта:

- `src/api/types.ts` — DTO; `client.ts` — транспорт и безопасные ошибки;
- `src/api/queries.ts` — кеш, отмена запросов, ключи аккаунта/фильтров и пагинация;
- `src/features/` — обзор, история, импорт и баннеры;
- `src/components/` — переиспользуемые UI-примитивы;
- `src/lib/` — форматирование времени, редкости и счётчиков;
- `src/styles.css` — токены и адаптивная тема из макета.

TanStack Query изолирует данные разных аккаунтов и отменяет устаревшие запросы.
После успешного импорта инвалидируются accounts/summary/pity/pulls. Сам URL
импорта не передаётся в mutation cache; в sessionStorage попадает только job ID.
Перезагрузка вкладки возобновляет наблюдение за заданием, но не повторяет POST.

`adapters/webui` раздаёт собранную SPA, не затрагивая application/domain.
В production фронтенд и API находятся на одном origin. В разработке эту же
границу сохраняет Vite proxy. Статику позднее можно вынести в CDN/reverse proxy.
Все UI-данные приходят через API: замена SQLite на PostgreSQL не требует
переписывания фронтенда. Баннеры запрашиваются через `/api/v1/banners?game=…`,
без привязки к аккаунту и без демонстрационных подстановок.

```text
cmd/api
  └── adapters/httpapi ──> application ──> domain
                              │              ▲
                              └── ports ─────┘
                                  ▲
             adapters/sqlite ─────┼──── adapters/gacha
             adapters/queue  ─────┘
```

Зависимости направлены внутрь. Домен не знает об HTTP, SQLite или форматах
ответов игровых API. Application-слой управляет заданием синхронизации,
проверяет принадлежность UID и вызывает порты. Адаптеры реализуют порты.

## Поток синхронизации

1. `POST /api/v1/sync-jobs` проверяет игру и создаёт запись `queued`.
2. Полный URL истории помещается только в ограниченную очередь памяти.
3. Worker отмечает задание как `running` и вызывает соответствующий адаптер.
4. Адаптер разрешает только известные официальные домены и сам конструирует
   адрес API. Это не позволяет превратить импорт в SSRF-прокси.
5. Ответ нормализуется в `domain.Pull`.
6. Аккаунт и крутки сохраняются одной транзакцией. Уникальность
   `(account_id, external_id)` делает повторный импорт безопасным.
7. Задание получает `completed` либо безопасную ошибку без credential.

HoYo импортируется страницами по 20 записей с курсором `end_id`. При повторной
синхронизации клиент останавливается на последнем сохранённом ID каждого
source pool. Kuro сейчас возвращает целый pool одним ответом, поэтому все
записи проходят через идемпотентный upsert.

## Расписание баннеров

`application.BannerService` зависит от отдельных портов `BannerSource` и
`BannerRepository`. HTTP-адаптер Ennead/Kuro нормализует ответы в доменные DTO;
SQLite хранит последний успешный снимок каждой игры в `banner_schedules`.
Перенос этой функции на PostgreSQL требует реализации `BannerRepository`,
но не изменения фронтенда или парсеров.

TTL снимка — 15 минут. Процесс прогревает кеш при старте и проверяет его каждые
5 минут. Запрос пользователя также обновляет просроченный снимок. Для каждой
игры объединяются конкурентные обновления; upstream имеет таймаут 10 секунд
и паузу 60 секунд после ошибки. При недоступности источника возвращается
последний снимок с `stale=true`, исходной датой загрузки и предупреждением.
Без снимка — `503`. Статусы пересчитываются даже для старого кеша: завершённый
баннер не остаётся «текущим» из-за сбоя источника.

У HoYo читается структурированный calendar Ennead; у WuWa — текст официального
английского объявления. HTML не попадает в интерфейс. Даты публикации новости
не используются как длительность баннера. Региональные ограничения отмечены
в `time_note`; неизвестные даты возвращаются как `null`. Изображения разрешены
только с перечисленных HTTPS-доменов игровых CDN и Enka, совпадающих с CSP фронтенда.

При нескольких инстансах API локальную блокировку обновления нужно заменить
распределённой арендой или выделить один refresh worker, чтобы не дублировать
запросы к источникам.

Поле `BannerItem.art_url` добавляет независимый порт `BannerArtwork` при чтении
расписания (в том числе уже сохранённого снимка). Адаптер Enka сопоставляет игровые
ID с полноразмерными артами Genshin/HSR/ZZZ, кеширует три каталога на 6 часов и
ограничивает попытку загрузки 1,5 секундами с минутной паузой после сбоя. Ошибка
артов не влияет на расписание. URL строятся только из проверенных путей каталогов
на фиксированном домене, а не из локализованных имён. В браузере при ошибке
изображения остаётся небольшое превью, без растягивания иконки.

## Pity

`pool_family` предназначен для интерфейса и фильтрации, а `pity_group` — для
математики. Это намеренно разные поля: например, HSR types `11` и `21` оба
являются limited character, но их состояние нельзя бездоказательно объединять.

Если в сохранённой истории присутствует последняя 5★/4★, счётчик имеет
`certainty=exact`. Если история начинается позже предыдущего редкого предмета,
возвращается `at_least`. Гарант пока имеет `unknown`: для него нужен отдельный
исторический каталог составов баннеров.

## SQLite и переход на PostgreSQL

SQLite является только реализацией `ports.Repository`. Для PostgreSQL нужно
добавить новый пакет, например `internal/adapters/storage/postgres`, реализовать
тот же интерфейс и заменить wiring в `cmd/api`. Domain, application и HTTP API
не меняются.

Схема уже использует:

- строковые UUID вместо SQLite autoincrement;
- явные уникальные ключи;
- UTC RFC3339 для служебных времён;
- исходное локальное время крутки без опасной конвертации часового пояса;
- keyset, а не offset-пагинацию.

## План масштабирования

### Один процесс

SQLite WAL, несколько worker-ов и bounded in-memory queue. Подходит для
локального приложения и небольшого self-hosted инстанса.

`GET /accounts/{id}/summary` агрегирует статистику в SQL без передачи полной
истории в браузер. Фильтры pool_family/rarity и курсор истории также серверные.
Текущий endpoint pity всё ещё читает историю аккаунта целиком на сервере;
это известная граница масштабирования, а не решённая задача высокой нагрузки.

### Несколько процессов

- PostgreSQL как source of truth;
- durable queue для метаданных задания;
- credential store с шифрованием и коротким TTL, а в очереди только reference;
- блокировка синхронизации по `(game, account_id)`;
- отдельные лимиты и backoff для каждого upstream;
- transactional outbox между записью задания и публикацией сообщения.

### Высокая нагрузка

- материализованный read model для pity/statistics;
- Redis-кеш только для производных данных;
- OpenTelemetry traces/metrics;
- горизонтально масштабируемые API и provider-specific workers;
- PostgreSQL partitioning по account/времени только после измерений.

## Перед публичным развёртыванием

Текущий API локальный и single-tenant. Перед доступом из интернета обязательны:
аутентификация, `tenant_id` во всех ключах/запросах, rate limiting, CORS allowlist,
TLS, лимит одновременных sync на пользователя и политика удаления данных.
Сейчас unsafe cross-origin запросы отсекает Go CrossOriginProtection, а SPA
отдаёт CSP и Referrer-Policy. Это не заменяет авторизацию. По умолчанию локальный
процесс привязан к loopback; Docker следует публиковать только на 127.0.0.1.
